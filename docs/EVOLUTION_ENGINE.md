# Synapse Evolution Engine — Stage 1 (experimental)

**Owner: Cory Davis / NavisWORLD.** This development branch is isolated from
stable Synapse alpha.4 and the pending alpha.5 image.

## What is implemented

The first evolution loop is **OBSERVE → PROPOSE (external model) → VALIDATE →
STAGE → RECEIPT → HUMAN REVIEW**. A model (RAWRPHØS, SmolLM, a cloud provider
or another replaceable adapter) may emit proposal JSON. In this milestone,
Synapse does not invoke a model, grant it shell access, execute proposed code,
compile it, modify the running OS or merge a branch. Those are subsequent
independent gates, not currently proven capabilities.

Two developer-repo CLI entry points:

- PYTHONPATH=src python3 -m synapse.cli evolve observe --repo .
  Reads bounded telemetry plus the local clean Git HEAD, excluding hostnames,
  secrets, tokens, personal memory and full sensor data. Nothing is sent to a model.
- PYTHONPATH=src python3 -m synapse.cli evolve stage proposal.json --repo . --output /tmp/synapse-review
  Validates base commit and original SHA-256 for every file, refuses dirty
  source and forbidden paths, parses changed Python without executing it,
  creates a detached separate local Git copy (no remote) outside the repo,
  and writes PATCH_REVIEW.diff and RECEIPT.json next to its checkout folder.

The model label in a proposal is **unverified provenance**, never proof of
which model generated it. Snapshot and receipt hashes describe local bytes,
not claims that a patch is correct, safe, faster or approved.

## Proposal JSON v1

Use the exact output of git rev-parse HEAD for base_commit. Compute
before_sha256 from exact tracked file bytes, not a guess.

~~~json
{
  "schema": "synapse.evolution.proposal.v1",
  "base_commit": "<40-character clean HEAD SHA>",
  "goal": "Make a specific measurable improvement.",
  "model_label": "rawrphos-native (claimed; not independently verified)",
  "changes": [
    {
      "path": "docs/UI.md",
      "before_sha256": "<64-character SHA-256 of current docs/UI.md>",
      "after_text": "<complete proposed replacement file contents>"
    }
  ]
}
~~~

The changes array is an allowlisted existing tracked-file replacement:
up to three changes, up to 64 KB each. Stage 1 permits one-level files under
src/synapse/*.py, tests/*.py, and docs/*.md only. Protected authority
surfaces (evolution.py, cli.py, agent.py, __init__.py), arbitrary
scripts/workflows, boot/install assets, credentials, kernel configuration
and symlink paths are rejected. Tests generated by models remain untrusted.

The source commit and original file digest must match. If a user or another
agent changes the repo, make a fresh observation and re-propose:
**never silently rebase a model-generated change**.

## Stage 1.5 — opt-in real local model adapter

Stage 1.5 can send a single bounded, user-approved task to an existing Beast
Box runtime using an explicitly chosen LOCAL Ollama or compatible model.
Neither the Vercel website password nor a cloud provider is used here.
The exact source path, clean base Git commit, original SHA-256, source bytes,
and strict replacement proposal schema go into the bounded task packet.

PREPARE ONLY, no model invocation:

    PYTHONPATH=src python3 -m synapse.cli evolve prepare --repo . \
      --path src/synapse/hardware.py --goal 'Suggest one measurable improvement.'

OPTIONAL one-turn live local inference, using an owner-installed model:

    PYTHONPATH=src python3 -m synapse.cli evolve local --repo . \
      --path src/synapse/hardware.py \
      --goal 'Suggest one measurable improvement.' \
      --beast-executable /opt/synapse/beast-runtime/bin/beastbox \
      --beast-data-dir /home/owner/.local/share/beastbox/beastos-web \
      --provider ollama --model OWNER_INSTALLED_MODEL_NAME \
      --url http://127.0.0.1:11434 \
      --output /tmp/synapse-evolution-review \
      --approve-code-in-memory

The final flag is mandatory because Beast can retain selected source text and
the completed exchange in the chosen continuity directory. Use a separate
disposable owner-owned Beast data directory if the experiment should not join
your ongoing memory. Inspect exactly what code is being sent.

The adapter rejects remote URLs, reference/fixture providers, missing consent,
ambiguous or invalid JSON, stale hashes, changed source and unauthorized edits.
It supplies no remote approval, inherited cloud keys, shell, OS authority or
automatic fallback. Model output is strictly a proposal. Its label is NOT
independent model-origin attestation.

The CI model tests use an explicitly injected stub reply; they do not claim
that a real model ran. A genuine inference receipt and independent disposable
VM evaluation remain separate milestones.

## Where autonomy begins — and where it stops

The current Stage 1 API is a proposal handoff boundary. A later model
adapter can populate JSON and request staging, but a detached checkout is
**not a hardened sandbox**. Do not execute untrusted generated code or
use that checkout as a credential-bearing development environment.
Static Python parsing is not evidence of runtime safety.

Stage 2 requires a separate disposable, credential-free VM evaluator which
receives only staged source plus versioned tests. Disconnect networking by
default; enforce CPU/memory/time limits; collect baseline vs candidate
results and reproducible boot, test and provenance receipts. Avoid the
host Docker socket, root filesystem or owner credentials.

Stage 3 adds independently enforced authority that can create *draft PRs
only* on approved development branches, after security and behavior gates.
Do not auto-merge, sign releases, restart production, modify physical disks
or firmware, trigger cloud charges, transfer old model grants or enable
self-updates without explicit owner approval and a rollback path.

**MODEL ≠ MEMORY. MODEL ≠ STATE. MODEL ≠ AUTHORITY.**

Beast/COSMOS continuity stays external to the replaceable model and disposable
test VM. A model-written diff is untrusted data, not permission to self-update.

## Evidence gates

The narrow .github/workflows/synapse-evolution-source.yml workflow tests the
Stage 1 engine/CLI security invariants. This is not a live alpha.5 rebuild,
not validation of an arbitrary generated patch, and not an end-to-end
self-updating operating system.
