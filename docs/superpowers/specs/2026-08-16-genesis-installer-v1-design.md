# COSMOS // GENESIS v1 Design

## Goal

Extend Synapse OS Phone Bootstrap into a controlled one-touch reimage workflow for an intentionally prepared, owner-controlled Chromebook. The phone provides the user interface and authenticated install request. A laptop-side GENESIS agent performs hardware inspection, image verification, destructive-install arming, installer staging, and status reporting. A dedicated installer environment performs the actual internal-disk replacement.

The first physical target is the ASUS Chromebook CX1700CKA / `GALLOP` profile already present in Synapse OS hardware detection.

## Scope

GENESIS v1 covers:

- a custom single-file `phone-bootstrap/GENESIS.html` phone control surface;
- a versioned local `/v2` API layered beside the existing `/v1` Phone Bootstrap API;
- authenticated laptop discovery and hardware/certification reporting;
- Synapse image manifest/hash verification;
- deterministic internal-disk discovery with removable-media rejection;
- an explicit destructive arming challenge;
- staging a signed/hashed install plan for a dedicated installer environment;
- installer receipt generation and progress/status reporting;
- post-install Synapse/COSMOS bootstrap intent;
- unit/integration tests and CI checks for all non-hardware-destructive logic.

GENESIS v1 does not silently disable Chromebook firmware write protection, bypass firmware security, expose a generic shell endpoint, accept arbitrary disk-write commands, or modify unrelated devices.

## User experience

The phone opens `GENESIS.html` and sees:

1. **CONNECT**
2. authenticated laptop identity and `GALLOP`/hardware profile
3. power, RAM, storage, boot mode, and target-disk preflight
4. Synapse image/manifest metadata and verification state
5. a destructive warning that ChromeOS/internal-storage contents will be replaced
6. **HOLD TO INSTALL SYNAPSE OS**
7. live progress from staging through installer handoff
8. install receipt and final status

The destructive action requires a press-and-hold confirmation in the browser plus a short-lived server-issued arm challenge. A normal click or replayed request is insufficient.

## Architecture

```text
IPHONE / GENESIS.html
        |
        | HTTP over trusted routed USB/local link
        | X-Synapse-Token + short-lived arm challenge
        v
SYNAPSE GENESIS AGENT (:8787)
        |
        +-- hardware probe / GALLOP profile
        +-- block-device inventory
        +-- image manifest + SHA-256 verification
        +-- install-plan generation
        +-- receipt generation
        +-- installer staging
        +-- reboot/handoff request
        |
        v
DEDICATED GENESIS INSTALLER ENVIRONMENT
        |
        +-- re-probe hardware
        +-- re-identify unique internal target
        +-- re-verify staged image + manifest
        +-- write Synapse OS image to internal target
        +-- sync / verify expected partitions/filesystem markers
        +-- preserve install receipt
        +-- reboot into Synapse OS
        |
        v
SYNAPSE OS
        +-- Phone Bootstrap service
        +-- COSMOS bootstrap/activation
```

The browser never receives raw shell capability. All privileged actions are fixed-purpose operations implemented by the GENESIS agent/installer.

## API v2

Public health:

- `GET /v2/health`

Authenticated read operations:

- `GET /v2/device`
- `GET /v2/preflight`
- `GET /v2/image`
- `GET /v2/install/status`
- `GET /v2/install/receipt`

Authenticated state-changing operations:

- `POST /v2/hello`
- `POST /v2/install/arm`
- `POST /v2/install/start`

There is no `/shell`, `/exec`, generic `/disk/write`, firmware-unlock, credential, persistence, or monitoring-disable endpoint.

## Authentication and arming

Existing Phone Bootstrap pairing-token authentication remains required.

`POST /v2/install/arm` succeeds only when preflight is safe and returns a random one-time challenge containing:

- `challenge_id`
- `device_fingerprint`
- `target_disk_id`
- `image_sha256`
- `issued_at`
- `expires_at`

The challenge is stored only in memory by the daemon, expires quickly, and is consumed exactly once.

`POST /v2/install/start` must include the challenge ID and an exact acknowledgement string generated by the UI. The server rejects expired, replayed, device-mismatched, target-mismatched, or image-mismatched challenges.

## Hardware and disk safety

GENESIS must not infer the target from `/dev/sda` or another hard-coded path.

The preflight inventory uses Linux block-device metadata and selects a target only when exactly one eligible internal, non-removable whole-disk device exists. It rejects:

- `RM=1` removable devices;
- USB transport targets;
- loop, zram, optical, device-mapper, and partition nodes;
- the device containing the currently mounted installer/source filesystem when it is identifiable;
- ambiguous multiple-internal-disk systems until a future explicitly supported selection mechanism exists.

The API returns stable disk identity fields where available: kernel path, model, serial, transport, size, rotational/removable flags, and a derived fingerprint.

`GALLOP` is a known physical target but not treated as physically certified until the real-device certification checklist passes.

## Image model

GENESIS uses a fixed Synapse image manifest rather than an arbitrary URL supplied by the phone.

The daemon configuration identifies the approved manifest location or staged manifest path. The manifest contains at minimum:

- format/version;
- Synapse OS version;
- architecture;
- image filename;
- exact byte size;
- SHA-256 digest;
- optional detached signature metadata;
- build commit;
- license/provenance identifiers.

The phone cannot replace the repository/image URL in the install request.

Before arming, the daemon must verify:

- architecture compatibility;
- image exists and size matches;
- SHA-256 matches the manifest;
- provenance/license markers are present in the manifest;
- target disk is large enough;
- adequate power/battery state is available;
- hardware/boot-mode prerequisites are satisfied.

A detached cryptographic signature verifier may be enabled when a project signing key is configured. GENESIS must distinguish `hash-verified` from `signature-verified`; it must not claim a signature verification that did not occur.

## Installer handoff

The running source OS must not overwrite the disk from which it is executing.

GENESIS v1 therefore stages an immutable install-plan JSON plus the verified image into an installer-accessible location and invokes a fixed configured handoff command/service. The handoff adapter is server configuration, not request-controlled input.

The default repository implementation supports two modes:

- **safe simulation mode** for tests and normal development, which writes no disks;
- **installer mode** enabled only by explicit daemon configuration inside the dedicated GENESIS installer environment.

The installer-mode writer accepts only the prevalidated install plan, revalidates the device fingerprint and image digest, and refuses all ad-hoc paths or commands.

## Actual disk-write implementation

Inside the dedicated installer environment, the fixed writer may use a standard raw-image copy tool such as `dd` or an equivalent block-copy primitive, but only after all server-side checks pass. The invoked command is constructed internally from validated fixed fields and never accepts shell text from the API or browser.

After write completion it runs `sync`, re-reads partition metadata, and checks expected Synapse OS installation markers before reporting success. Failure leaves the receipt in a failed state and does not falsely mark the device ready.

## Recovery receipt

Every armed attempt creates a structured JSON receipt containing:

- receipt format/version;
- timestamp;
- hardware profile / HWID / architecture;
- device fingerprint;
- target disk metadata;
- Synapse image version, build commit, size and SHA-256;
- license identifier;
- Zenodo DOI `10.5281/zenodo.17574447`;
- arm challenge ID;
- install phase transitions;
- final success/failure state and error summary.

The receipt is available through `GET /v2/install/receipt` and stored locally. It is evidence of the GENESIS transaction, not a backup of the previous ChromeOS installation.

## UI design

`GENESIS.html` remains a single-file offline-capable HTML/CSS/JavaScript client. It uses the existing cosmic Synapse visual language while being more explicit about destructive state.

Primary states:

- `DISCONNECTED`
- `CONNECTED`
- `PREFLIGHT BLOCKED`
- `READY TO ARM`
- `ARMED`
- `STAGING`
- `HANDOFF REQUIRED/IN PROGRESS`
- `INSTALLING`
- `VERIFYING`
- `COMPLETE`
- `FAILED`

The install control is disabled unless the device, disk, image and power checks are green.

## Error handling

The server returns structured errors with stable error codes such as:

- `AUTH_REQUIRED`
- `PREFLIGHT_FAILED`
- `TARGET_AMBIGUOUS`
- `TARGET_REMOVABLE`
- `IMAGE_MISSING`
- `IMAGE_HASH_MISMATCH`
- `ARCH_MISMATCH`
- `POWER_INSUFFICIENT`
- `ARM_EXPIRED`
- `ARM_REPLAYED`
- `ARM_MISMATCH`
- `INSTALLER_DISABLED`
- `HANDOFF_FAILED`
- `WRITE_FAILED`
- `VERIFY_FAILED`

The UI renders the code plus a human-readable remediation message.

## Testing

Required non-destructive tests:

- device and block-inventory parsing fixtures;
- unique-internal-target selection;
- removable/USB rejection;
- ambiguous-target rejection;
- manifest size/hash verification;
- architecture mismatch rejection;
- short-lived arm challenge issuance;
- replay/expiry/device/image/target mismatch rejection;
- install start refused when installer mode is disabled;
- simulation-mode full state-machine completion;
- receipt completeness and DOI/license provenance;
- `/v2` API authentication/HTTP integration;
- `GENESIS.html` route/control smoke tests;
- existing `make check` remains green;
- amd64 ISO build, generated-filesystem inspection and QEMU boot remain green.

Real destructive install is not exercised against a CI runner disk. Physical install certification is a separate GALLOP hardware acceptance procedure.

## Physical readiness boundary

The repository can be made code-complete and VM-tested before the Chromebook is connected. That does not mean ChatGPT itself can dial into a local USB/private endpoint from this conversation. When the Chromebook is physically prepared and the GENESIS agent is running, the phone HTML talks directly to that local API.

GENESIS reports `PHYSICAL PREPARATION REQUIRED` rather than attempting to bypass Chromebook firmware/write-protection prerequisites.

## Success criteria

GENESIS v1 is implementation-complete when:

1. the v2 API, UI, manifest verifier, disk safety layer, arm challenge, receipt, staging adapter and installer-mode writer exist;
2. all non-destructive unit/integration tests pass;
3. the existing Synapse OS amd64 image builds and QEMU-boots with GENESIS assets included;
4. CI verifies `GENESIS.html`, the GENESIS agent modules and provenance/license files inside the image;
5. destructive behavior remains disabled outside an explicitly configured dedicated installer environment;
6. GALLOP remains labeled `physical-target` until the real Chromebook install test passes.
